# Contributing

Issues and pull requests welcome. Contributions are licensed under the [MIT License](./LICENSE). Please follow the [code of conduct](./CODE_OF_CONDUCT.md).

A change to the HTML an existing document renders to is a breaking change. Keep the public export in `src/public.ts` stable.

```bash
npm install
npm run typecheck
npm test
```

`zod` is a peer dependency (`^4`). Node.js 18+.

## How your pull request lands

`@unitpost/email` is developed in Unitpost's main repository, alongside the product that uses it. This repository is its published mirror: every commit on `main` is a snapshot synced from there (`Sync from unitpostcom/unitpost@<sha>`). So pull requests are not merged here; they are imported.

1. Open your pull request against `main`. CI runs the typecheck and the tests.
2. A maintainer reviews it here. When it is ready, they label it `import` and import it. The bot labels it `imported` and comments to say so.
3. The change is reviewed once more upstream and merged there, with you as the commit's author.
4. When it reaches the next sync of this repository, the bot comments **"Landed in"** with a link to the public commit and closes your pull request. That commit credits you as a co-author (`Co-authored-by`), so it shows on your GitHub profile.

Closed rather than merged is expected: your change is in `main`, through the sync commit.

### Keep your branch on a recent `main`

The import finds the sync commit your branch starts from, so branch from (or merge) the current `main`, and keep the generated files out of your change:

- `scripts/node-test.mjs` is generated by the sync. A pull request that edits it cannot be imported; describe the change in an issue instead.
- No symlinks, no submodules, nothing under `dist/`, `node_modules/` or `coverage/`.

If a maintainer asks you to update a stale pull request (it conflicts, or starts from a commit that is not a sync):

```bash
git fetch upstream            # upstream = https://github.com/unitpostcom/email
git rebase upstream/main      # or: git merge upstream/main
git push --force-with-lease
```

Push follow-up changes to the same branch. The maintainer re-imports it after reviewing them; pushing new commits after the import does not update the imported copy by itself.
